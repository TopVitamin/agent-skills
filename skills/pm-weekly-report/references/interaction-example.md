# 从碎片到成稿的交互示例

全篇为虚拟示例，展示内容社区产品的一次完整交互。界面按钮用文字描述，由宿主可用对话工具实现；不照抄工具名称。

## 原始输入

“搜索改了，研发说好了；访谈做了6个，搜不到东西很多；通知那个方案讨论过了。下周想搞搜索验证。就这两个项目，没别的了。”

## 第一轮

助手识别已有事实：访谈数量明确；搜索修复与验证状态不明；通知只有讨论；用户已说明仅两个项目且无补充，不重复查漏。

通过对话工具询问：

- “搜索目前是哪种状态？”选项：研发已修复、待验证／已验证、待上线／已上线；允许自由说明。
- “通知方案讨论后形成了什么结论？另外，访谈中有多少人遇到搜索问题、下周是否准备推进通知方案？”使用自由输入。

用户答：“搜索修好了还没测。6人里4人提到搜索不到想要的内容。通知还没定，重点是消息太多，想先弄清用户接受什么频率。下周也研究这个。两个项目就按实际写。”

助手据此结束第一轮，不推断搜索问题已解决，不将4/6扩展为全体用户比例。

## 第二轮

展示简短方案：

| 模块 | 拟采用内容 |
|---|---|
| 完成工作 | 搜索体验优化：访谈、修复跟进两条；消息通知方案：方案讨论一条，按已确认数量例外保留 |
| 总结 | 搜索访谈反馈与待验证状态，通知频率仍在探索 |
| 计划 | 先验证搜索修复，再研究通知频率 |

随后通过对话工具提供“按此方案成稿／调整方案”，允许自由输入。用户选择“按此方案成稿”。此处必须收到实际回复，不能将工具已弹出当成确认。

## 成稿

```markdown
> 虚拟示例，仅展示交互与表达，不代表真实项目记录。

## 一、本周完成工作

### 搜索体验优化

- 完成6位用户访谈，其中4位提到难以搜索到所需内容。
- 跟进搜索问题修复，研发反馈已完成修复，当前尚待验证。

### 消息通知方案

- 参与消息通知方案讨论，重点关注通知过多的问题，合理发送频率尚未确定。

## 二、本周工作总结

本轮6位受访用户中有4位提到搜索体验问题。搜索修复已由研发反馈完成，下周需要通过验证确认效果；通知方案仍以了解用户可接受的频率为主，暂未形成确定结论。

## 三、下周工作计划

1. 验证搜索问题修复情况，重点关注**用户反馈的搜索问题是否得到改善**。
2. 继续研究消息通知频率，了解用户的接受程度，为方案讨论提供依据。
```

此示例的两组及单条分组是经用户确认的例外，不作为默认数量模板。虚拟标识仅用于示例分享，正式周报不输出。


## 正常规模的第二轮提纲示意

以下为另一份虚拟材料已完成第一轮后的组织方式，仅展示提纲，不新增待确认事实。

| 完成工作分组及顺序 | 条数与事项关键词 |
|---|---|
| 搜索体验优化 | 2条：用户访谈、问题复测 |
| 消息通知方案 | 2条：发送频率讨论、原型调整 |
| 创作者工具 | 2条：发布流程走查、帮助文档更新 |
| 数据分析与协作 | 2条：指标口径核对、业务培训 |

总结拟突出搜索验证进展与通知方案未决事项；下周计划按搜索优化、通知评审、创作者工具研发跟进排序。随后通过可用对话工具确认方案，而不是直接成稿。
